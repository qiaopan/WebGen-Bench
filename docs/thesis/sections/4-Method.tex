\section{Problem Formulation}
\label{sec:formulation}
A run processes the tasks $t_1,\dots,t_n$ ($n=101$) in a fixed order. Task $t_i$ has a requirement $r_i$ and hidden test cases $c_{i,1},\dots,c_{i,m_i}$. A generator $G$ with fixed weights maps a prompt $x_i$ to a project $y_i=G(x_i)$, which the evaluator $E$ scores as $a_i=E(y_i, c_{i,\cdot})\in[0,1]$ with the accuracy defined in \Cref{chap:setup}. Under No Memory, $x_i=r_i$. With memory, the prompt is
\begin{equation}
x_i = r_i \oplus f(r_i, M_{i-1}), \qquad M_i = u\bigl(M_{i-1}, r_i, y_i, \tau_i, a_i\bigr),
\end{equation}
where $M_0=\emptyset$, $f$ selects and formats memory for the current requirement, $\oplus$ appends text after the requirement, $\tau_i$ is the evaluator transcript, and $u$ reflects on the finished task and updates the memory. Two constraints make the comparison fair: $f$ only reads $M_{i-1}$, which is built from earlier tasks, so the hidden evaluation of $t_i$ never reaches its own prompt; and $G$, $E$ and the protocol are identical across arms. The question is whether the mean of $a_i$ is higher with memory than with $x_i=r_i$, and which design of $f$ and $u$ achieves it. \Cref{alg:pipeline} gives the final design, which \Cref{sec:pipeline} specifies in full; \Cref{sec:nm-failures,sec:history} first explain the failures that motivated each component.

\begin{algorithm}[ht]
\caption{Cross-task memory for one run (final version).}
\label{alg:pipeline}
\begin{algorithmic}[1]
\State $M \gets \emptyset$; \quad $F \gets \emptyset$ \Comment{lessons; code facts of earlier sites}
\For{$i = 1,\dots,n$}
  \State $L \gets \textsc{Checklist}(r_i)$ \Comment{memory model splits the requirement}
  \State attach to $L$ the lessons in $M$ judged a hard match for $r_i$ (at most three)
  \State $C \gets \textsc{ActivateEntries}(F)$ \Comment{trigger: 2 tasks, or 1 if site-breaking}
  \State $P \gets \textsc{SelectAndVerify}(C, \{y_j : j<i,\ a_j \ge 0.5\})$ \Comment{at most three fragments}
  \State $x_i \gets r_i \oplus L \oplus P$; \quad $y_i \gets G(x_i)$; \quad $a_i \gets E(y_i)$
  \State reflect on $(y_i,\tau_i,a_i)$; add lessons to $M$ after deduplication; update utilities
  \State $F \gets F \cup \textsc{StaticAnalyse}(y_i)$; \quad \textsc{UpdateVersion}$(C, F)$
\EndFor
\end{algorithmic}
\end{algorithm}

\noindent\textsc{StaticAnalyse} compiles every component of a site with \texttt{@vue/compiler-sfc} and records undeclared package imports, Vue functions used without import, and compile errors. \textsc{ActivateEntries} turns each recorded problem into a code-pool entry once its trigger holds. \textsc{SelectAndVerify} takes, for each active entry, the key lines that the memory model picks from an earlier successful site and accepts them only if they are verbatim, at most 15 lines, free of \texttt{<script>}/\texttt{<template>} tag lines, and include the needed import and a line that uses it; after two failed picks a rule-based extraction is used. \textsc{UpdateVersion} adds a new version of an entry only when its example covers strictly more of the needed functions, and keeps the old one. \Cref{sec:codepool} gives the details and \Cref{tab:params} the constants.

\section{Starting Point: Why No Memory Fails}
\label{sec:nm-failures}
We began by inspecting the code that No Memory actually produced, rather than its scores. Two findings shaped everything that followed.

\paragraph{Blank pages from basic errors.} Bolt.diy's Vue template declares only \texttt{vue} as a dependency, and WebGen-LM-7B never edits \texttt{package.json} (0 of 81 inspected responses). When it imports \texttt{vue-router} or uses a Vue function such as \texttt{ref} without importing it, the whole site renders as a blank page and every test case fails. In an early Long Memory run, 26 of 74 tasks were blank, 19 of them because of an undeclared \texttt{vue-router} import. Many zero-score tasks therefore fail before their functional difficulty can be assessed: the site does not render because of a basic error that the model repeats.

\paragraph{Text is not followed.} In a targeted diagnostic, not a powered experiment, we took nine tasks that had produced blank pages, kept their original prompts, and added a single sentence, phrased in several ways (``add vue-router to package.json'', ``do not use vue-router'', ``put pages in App.vue with \texttt{ref} and \texttt{v-if}'', or the same sentence at both the start and the end). None recovered more than one task in three. Each phrasing was tried on three of the nine tasks; a task counted as recovered when the generated code imported no undeclared package and compiled. A ten-line code example of the same idea, tried on all nine, recovered seven. This matches the observation that small models follow long textual guidance poorly~\cite{harada2025curse,li2025smallmodels} and suggested that memory should be delivered as code.

\paragraph{From text to code.} The first memory followed ExpeL-style reflection: after each task the memory model wrote cases (trigger, observation, cause, preventative action) with evidence, retrieved later as guidance. Reflection rules teach a method of investigation, never answers, so that the memory is learned rather than designed. After a scaffold bug was fixed (Bolt.diy treated a line break as ``send'' and dropped the rest of the prompt), long guidance made the model build only the home page, and compressing it dropped features. The checklist of v4 keeps every requested feature visible and attaches lessons to the item they concern; v4 beat No Memory on the first 30 tasks (39.3\% vs 26.0\%) but not on the last 71 (27.8\% vs 29.5\%). The code pool of v6 replaced text by code, but its one-line example wrapped in \texttt{<script setup>} tags looked like a finished empty component and produced untouched scaffolds; v7 therefore admits, for missing-import entries, only verbatim fragments without tag lines that include a line using the imported function. Missing-package entries in v7 still showed a complete \texttt{App.vue} of an earlier site, because their example had to demonstrate page switching without the missing package. In the manifest order this caused two scaffolds; under shuffled orders it caused many (\Cref{fig:scaffold}); v8 to v9.1 change only the code pool to fix this (\Cref{sec:fix}). A planning step before generation was rejected: in five of five tasks the generator wrote only the plan and lost Bolt.diy's file format.

\section{Final Pipeline (v9.1)}
\label{sec:pipeline}
For each task, in order:
\begin{enumerate}
  \item \textbf{Requirement checklist.} The memory model splits the requirement into items (\Cref{sec:checklist}).
  \item \textbf{Retrieve lessons.} Functional lessons are retrieved by similarity and judged for applicability by the memory model; only hard matches are attached to checklist items. A small common pool adds site-wide lessons that contain a concrete code construct.
  \item \textbf{Code pool.} At most three verified fragments whose trigger condition holds (\Cref{sec:codepool}).
  \item \textbf{Generate and evaluate.} One generation by WebGen-LM-7B; official functional and appearance evaluation.
  \item \textbf{Reflect and store.} The memory model reflects on the evaluated task; new lessons are deduplicated against existing ones, utilities are updated, and code facts are computed for the code pool.
\end{enumerate}
The products of step 5 are read by steps 2 and 3 of later tasks; this is the only path through which tasks influence each other. \Cref{fig:prompt} shows the resulting prompt for one task; under No Memory the prompt is the first paragraph only.

\subsection{Requirement Checklist}
\label{sec:checklist}
The original requirement remains at the top of the prompt and is declared binding. The checklist below it repeats every requested feature, so that memory content cannot crowd a feature out of the model's attention~\cite{liu2024lost,wallace2024hierarchy}. Lessons are attached to the item they concern rather than listed separately, which avoids a separate list being read as the full scope of the task.

\subsection{Code Pool}
\label{sec:codepool}
The code pool is computed without an \gls{llm} for detection:
\begin{itemize}
  \item \textbf{Problem facts.} After each task, code analysis of the generated site records undeclared imports (\texttt{import:<package>}), Vue functions used without import (\texttt{vue-api}), and compile errors obtained by compiling each \gls{sfc} with \texttt{@vue/compiler-sfc} exactly as Vite would.
  \item \textbf{Trigger.} A problem key becomes active after it has appeared in two different tasks, following Metis's rule of promoting a procedure only after it recurs~\cite{dai2026metis}. Whole-site failures that code detects objectively (an undeclared package, a compile error) become active after one occurrence. Missing-import and compile-error entries apply to every Vue site; other entries are applied only if the memory model judges their condition to hold for the requirement.
  \item \textbf{Source.} The example comes from the chain's own earlier websites that scored at least 0.5 and compile. The threshold of 0.5 is a design choice (at least half the checks passed), not a tuned value. Successful sites supply \emph{how} to write it; failed sites decide \emph{when} it is needed~\cite{reasoningbank2025}.
  \item \textbf{Fragment selection.} The memory model picks the key lines; code then verifies that the lines are verbatim from the source file, contain at most 15 lines, contain no \texttt{<script>}/\texttt{<template>} tag lines, and include the import of the most frequently missed function plus a line that calls it. If the model fails twice, a rule-based extraction is used. An entry is updated by adding a new version only when the new example covers strictly more of the needed functions; the old version is kept for provenance~\cite{ace2026}.
  \item \textbf{Slots.} At most three entries per task, at most one of them for a missing package.
\end{itemize}
\textit{Verified} in this dissertation means only that a fragment is verbatim from a source file that compiles and comes from a site with score $\ge 0.5$; it does not mean that the fragment is correct for the new task. Because the triggers are general, the code pool behaves partly like a learned prompt prefix: once active, many later tasks receive the same fragment. The fixed-prefix ablation (\Cref{sec:ablation}) separates this from learning. \Cref{tab:params} lists the constants of the final configuration. \todo{Planned (existing data): mean injected tokens per task and one stored entry as an example.}

\subsection{Memory Hygiene}
\begin{itemize}
  \item \textbf{Concrete only.} Common-pool entries without a code construct (for example \texttt{@click}, \texttt{v-if}, an \texttt{import} line) are dropped. Rewriting may generalise the \emph{condition} under which a lesson applies but not the \emph{action}.
  \item \textbf{Deduplication at storage time.} A new lesson is compared with similar stored lessons; if the memory model judges it to share the same root cause and fix, it is recorded as support for the old lesson instead of a new entry~\cite{chhikara2025mem0}.
  \item \textbf{Utility and retirement.} For each lesson we count injections $u$ and recurrences $r$ (the same problem reappearing after injection), and compute utility $(u - r + 1)/(u + 2)$~\cite{zhou2025memento,zhao2024expel}. Ranking uses support $\times$ severity $\times$ utility; a lesson injected at least five times with utility below 0.3 is no longer injected. Utility is a heuristic: a task after injection that does not repeat the problem may not have needed the lesson, and a lesson used on hard tasks can be penalised. The constants (two occurrences, five injections, 0.3) are design choices that were not tuned.
  \item \textbf{No hand-written conclusions.} Instructions to the reflection model describe how to investigate (follow the code path, trace styles from element to global stylesheet, list candidate causes and rule them out) but never what the answer is.
\end{itemize}
