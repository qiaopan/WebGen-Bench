\section{Benchmark and Protocol}
We use all 101 WebGen-Bench tasks. They come from 20 application domains of unequal size, from eight tasks each (company brochures, learning platforms, discussion forums, e-commerce) down to two (personal blogs, streaming, email clients). The benchmark's manifest order groups tasks into domain blocks; \Cref{sec:order-design} adds shuffled orders. We follow the official protocol: the generator produces the project once, there is no repair loop, and a project is passed to evaluation as soon as its dependencies install and the development server starts. Test cases without an evaluation record count as failed, as in the official scoring script. An earlier phase of this project used a stricter build gate (\texttt{vue-tsc}) and a more generous repair loop; those results are not comparable with the paper and are not reported as main results.

\Cref{fig:pipeline} shows one task in the evaluation pipeline. The memory module is the only component that differs between arms; the generator, the scaffold, the tester and the scoring are shared.

\section{How One Task Is Generated and Scored}
\label{sec:walkthrough}
This section follows one task through the unmodified system, so that it is clear what the memory later changes. Task 000006 asks for a solar dashboard:

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}
Please implement a solar dashboard to display real-time and historical solar
data. The dashboard should have functionalities for real-time data display,
historical data query, and chart analysis. [...] Configure the background color
to honeydew, with components using dark olive green.
\end{lstlisting}
\end{minipage}

\paragraph{Generation.} Under No Memory this text is the entire prompt. Bolt.diy is an open-source browser-based coding agent: it opens a starter project (for Vue, a Vite + Vue + TypeScript template whose \texttt{package.json} declares only \texttt{vue}), sends the requirement to the generator, and writes every file of the model's reply into the project. It then installs the dependencies and starts the development server. The generator has one reply; nothing in the official protocol inspects or repairs the code.

\paragraph{Functional testing.} Each task comes with hidden test cases, on average six. For task 000006 the first two are ``Verify the display of real-time solar power generation data'' and ``Test the display of real-time power consumption data'', each with an expected result. A WebVoyager-style \gls{gui} agent~\cite{he2024webvoyager} receives one test case at a time. At each step it sees a screenshot in which every interactive element carries a numbered box (\Cref{fig:walkthrough}b), chooses an action such as clicking element 1 or typing into a field, and finally answers YES, PARTIAL or NO. The agent has a fixed step budget; if it runs out before reaching the target, the case counts as failed.

\paragraph{Appearance grading.} A vision model grades a full-page screenshot from 1 to 5 for layout, colour and completeness. Both the tester and the grader are models acting as judges, which are known to have biases~\cite{zheng2023judge}; we therefore keep their raw transcripts and, in \Cref{sec:threats}, check a sample of their verdicts by hand.

\Cref{fig:walkthrough} shows what the tester saw for this task in two runs. Under No Memory the model imported the chart library \texttt{vue-chartjs}, which the template does not declare; Vite cannot resolve the import, the page shows only the error overlay, and all test cases fail. With the final memory the generator built the three requested views without the undeclared package, and all test cases passed.

\section{Models and Roles}
All models are self-hosted on the university CS ML cluster (two NVIDIA H200 GPUs per job, served with vLLM~\cite{kwon2023vllm}). No commercial \gls{llm} service is called. \Cref{tab:roles} lists the roles.

\paragraph{The generator.} WebGen-LM is a family of website-generation models (7B, 14B and 32B) released with WebGen-Bench~\cite{lu2025webgenbench}. Each is Qwen2.5-Coder-Instruct~\cite{hui2024qwencoder} of the same size, fine-tuned with supervised learning only. The training data come from WebGen-Instruct, 6,667 website instructions decontaminated against the benchmark: the authors ran DeepSeek-V3 in Bolt.diy on 2,000 of them and kept the 600 trajectories whose websites scored at least 3 for appearance. WebGen-LM-7B therefore already knows the Bolt.diy output format, which makes it the natural small baseline for this benchmark: it is not a general model prompted to build websites, but a model distilled for exactly this scaffold.

The memory model is deliberately different from the evaluator, so that reflection cannot copy the evaluator's grading behaviour. vLLM applies the model repository's generation configuration by default; WebGen-LM-7B ships with a repetition penalty that Bolt.diy never sends, so we disable it for the generator to match the paper's setting.

\section{Metrics}
For each task with $n$ test cases, of which $p$ pass and $q$ are partial,
\begin{equation}
\text{accuracy} = \frac{p + 0.5\,q}{n}.
\end{equation}
We report accuracy over all test cases, the mean appearance score (1--5), and the number of \emph{zero-score} tasks. Because test cases within a task are not independent, comparisons are paired by task rather than by test case: for two arms we report the mean per-task difference in accuracy with a 95\% percentile bootstrap \gls{ci} obtained by resampling tasks~\cite{efron1993bootstrap}, together with the numbers of tasks won, lost and tied. This interval is conditional on the observed runs: it reflects which tasks happened to be in the benchmark, but not the variation between repeated runs of the same memory chain (about five points, \Cref{sec:fix}), nor the dependence between tasks that a memory creates. We therefore say that an interval ``excludes zero'' rather than calling a gain significant. Accuracy pools test cases (micro); the learning curves average tasks (macro).

\section{Experimental Design}
\label{sec:design}
The memory designs we built fall into three families, shown in \Cref{fig:families} and described in \Cref{chap:method}. \emph{Text memory} (v1--v4) stores lessons written in natural language and adds them to the prompt; its last version, v4, adds the requirement checklist. \emph{Code memory} (v5--v7) keeps the checklist and adds a code pool of examples taken from the chain's own working websites. The \emph{final} family (v8--v9.1) changes only how the code pool selects and updates its examples. One version of each family was run on all 101 tasks, v4, v7 and v9.1, and in the rest of this dissertation the three names refer to these runs. Versions that were stopped part-way or never run on all tasks are described only in the design history (\Cref{sec:history}).

\section{Reproducing the Baseline}
No Memory on all 101 tasks reaches 28.5\% accuracy (paper: 28.4\%) with a mean appearance score of 2.35 (paper: 2.5 with GPT-4o) and 30 zero-score tasks. The near-identical aggregate accuracy is evidence that the self-hosted pipeline approximately reproduces the published baseline; the appearance grader differs, and task-level agreement cannot be measured because the paper's per-task outputs are not available.

\section{Reproducibility and Constraints}
Every run starts from an empty memory and stores its configuration file, task order, prompts, retrieved and injected memory, raw evaluator transcripts and scores; the key files of every run are archived in the project repository. The generator is decoded deterministically, so differences between arms come from the prompt rather than from sampling, although the \gls{gui} tester is not deterministic.

\paragraph{Hardware.} All experiments ran on one node of the School of Computer Science CS ML cluster (\texttt{foscsmlprd03}, seven NVIDIA H200 GPUs with 141\,GB of memory each, Slurm scheduler), with at most two GPUs per user. A single long-running job held two GPUs and served every model with vLLM; all arms and task orders shared these servers (\Cref{tab:hardware}). Two tasks were processed in parallel, while evaluation was serialised by a lock, because the evaluator restarts the website process manager. From the first job on 5 October 2026 to the end of the 7B runs, the project used about \todo{update} H200 GPU-hours.

\paragraph{Code and data availability.} The code, configuration files and the archived run records (prompts, injected memory, scores and memory databases of every run) are publicly available at \url{https://github.com/qiaopan/WebGen-Bench}; the run records are in \texttt{archive/phase2-webgen-2026-10/}.

The main constraint is compute. A task takes about twelve minutes with memory and six without, so one 101-task run takes about a day on our two GPUs. As in the original benchmark, each configuration is therefore run once per task order. We compensate by pairing comparisons by task, by repeating the No Memory baseline in three orders to measure its run-to-run variation, and by repeating the memory method across orders rather than within one.
