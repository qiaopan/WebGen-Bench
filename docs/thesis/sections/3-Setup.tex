\section{Benchmark and Protocol}
We use all 101 WebGen-Bench tasks. They come from 20 application domains with two to eight tasks each. The benchmark's manifest order groups tasks into domain blocks; \Cref{sec:order-design} adds shuffled orders. We follow the official protocol: the generator produces the project once, there is no repair loop, and a project is passed to evaluation as soon as its dependencies install and the development server starts. Test cases without an evaluation record count as failed, as in the official scoring script. An earlier phase of this project used a stricter build gate (\texttt{vue-tsc}) and a more generous repair loop; those results are not comparable with the paper and are not reported as main results.

\Cref{fig:pipeline} shows one task in the evaluation pipeline. The memory module is the only component that differs between arms; the generator, the scaffold, the tester and the scoring are shared.

\section{How One Task Is Generated and Scored}
\label{sec:walkthrough}
This section follows one task, 000006, through the unmodified system:

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}
Please implement a solar dashboard to display real-time and historical solar
data. [...] Configure the background color to honeydew, with components using
dark olive green.
\end{lstlisting}
\end{minipage}

Under No Memory this text is the entire prompt. Bolt.diy, an open-source browser-based coding agent, opens a Vite + Vue + TypeScript starter whose \texttt{package.json} declares only \texttt{vue}, writes every file of the generator's single reply into it, installs dependencies and starts the server. Each task has on average six hidden test cases (here, for example, ``Verify the display of real-time solar power generation data''). A WebVoyager-style \gls{gui} agent~\cite{he2024webvoyager} takes one case at a time, acts on screenshots in which interactive elements carry numbered boxes, and answers YES, PARTIAL or NO within a fixed step budget. A vision model grades a full-page screenshot from 1 to 5. Both are models acting as judges, which have known biases~\cite{zheng2023judge}; their raw transcripts are kept.

\Cref{fig:walkthrough} shows what the tester saw for this task in two runs. Under No Memory the model imported the chart library \texttt{vue-chartjs}, which the template does not declare; Vite cannot resolve the import, the page shows only the error overlay, and all test cases fail. With the final memory the generator built the three requested views without the undeclared package, and all test cases passed.

\section{Models and Roles}
All models are self-hosted on the university CS ML cluster (two NVIDIA H200 GPUs per job, served with vLLM~\cite{kwon2023vllm}). No commercial \gls{llm} service is called. \Cref{tab:roles} lists the roles.

\paragraph{The generator.} WebGen-LM-7B, released with WebGen-Bench~\cite{lu2025webgenbench}, is Qwen2.5-Coder-7B-Instruct~\cite{hui2024qwencoder} fine-tuned on Bolt.diy trajectories for instructions decontaminated against the benchmark. It already knows the Bolt.diy output format, which makes it the natural small baseline: a model distilled for exactly this scaffold.

The memory model is deliberately different from the evaluator, so that reflection cannot copy the evaluator's grading behaviour. vLLM applies the model repository's generation configuration by default; WebGen-LM-7B ships with a repetition penalty that Bolt.diy never sends, so we disable it for the generator to match the paper's setting.

\section{Metrics}
For each task with $n$ test cases, of which $p$ pass and $q$ are partial,
\begin{equation}
\text{accuracy} = \frac{p + 0.5\,q}{n}.
\end{equation}
We report accuracy over all test cases, the mean appearance score (1--5), and the number of \emph{zero-score} tasks. Because test cases within a task are not independent, comparisons are paired by task rather than by test case: for two arms we report the mean per-task difference in accuracy with a 95\% percentile bootstrap \gls{ci} obtained by resampling tasks~\cite{efron1993bootstrap}, together with the numbers of tasks won, lost and tied. This interval is conditional on the observed runs: it reflects which tasks happened to be in the benchmark, but not the variation between repeated runs of the same memory chain (about five points, \Cref{sec:fix}), nor the dependence between tasks that a memory creates. We therefore say that an interval ``excludes zero'' rather than calling a gain significant. Accuracy pools test cases (micro); the learning curves average tasks (macro).

\section{Experimental Design}
\label{sec:design}
We compare three memory designs, shown in \Cref{fig:families} and described in \Cref{chap:method}. \emph{Text memory} stores lessons written in natural language and attaches them to a requirement checklist. \emph{Code memory (whole-file)} keeps the checklist and adds a code pool of examples taken from the chain's own working websites; some of these examples are complete files. \emph{Code memory (fragments)}, the final method, shows only short verified fragments. We take it as the final method because it removed the scaffold failure under shuffled orders, not because it scores highest in every order: in the manifest order whole-file code memory scores higher (\Cref{sec:main}). The method was refined over several iterations; only these three designs were run on all 101 tasks, and only they are reported.\footnote{In the code repository these runs are labelled v4, v7 and v9.1.}

\section{Reproducing the Baseline}
No Memory on all 101 tasks reaches 28.5\% accuracy (paper: 28.4\%) with a mean appearance score of 2.35 (paper: 2.5 with GPT-4o) and 30 zero-score tasks. The near-identical aggregate accuracy is evidence that the self-hosted pipeline approximately reproduces the published baseline; the appearance grader differs, and task-level agreement cannot be measured because the paper's per-task outputs are not available.

\section{Reproducibility and Constraints}
Every run starts from an empty memory and stores its configuration file, task order, prompts, retrieved and injected memory, raw evaluator transcripts and scores; the key files of every run are archived in the project repository. The generator is decoded deterministically, so differences between arms come from the prompt rather than from sampling, although the \gls{gui} tester is not deterministic.

\paragraph{Hardware.} One long-running Slurm job on two NVIDIA H200 GPUs served all models with vLLM and was shared by all arms and orders; it used about \todo{update} H200 GPU-hours.

\paragraph{Code and data availability.} The code, configuration files and the archived run records (prompts, injected memory, scores and memory databases of every run) are publicly available at \url{https://github.com/qiaopan/WebGen-Bench}; the run records are in \texttt{archive/phase2-webgen-2026-10/}.

The main constraint is compute: a task takes about twelve minutes with memory and six without, so one 101-task run takes about a day. As in the original benchmark, each configuration is run once per order; comparisons are paired by task, and No Memory is repeated across orders to measure run-to-run variation.
