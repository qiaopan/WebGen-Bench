The final fragment method reaches 35.2\%, compared with 28.5\% for No Memory. Its paired gain is $+7.1$ [0.9, 13.1], with 44 wins, 28 losses, and 29 ties, and it reduces zero-score tasks from 30 to 20. Much of this difference comes from sites that run at all: 19 tasks score above zero only with memory, while 9 do so only without it. Among the 62 tasks for which both arms score above zero, the paired gain is $+2.6$ [$-3.2$, 8.5]. No Memory varies by only 0.7 points across three orders (\Cref{sec:order-design}). A memory chain varies more because early outcomes change its later memory (\Cref{sec:fix}). The intervals for text memory and the checklist-only control both include zero.

The intermediate whole-file design scores higher in manifest order (40.0\%, $+11.5$ [6.0, 16.9]). The final fragment method is $-4.4$ [$-9.8$, 1.0] against it in that order, but the advantage does not persist across task orders (\Cref{sec:order-design}). \Cref{tab:main} assigns an appearance score of zero to tasks without a working site. Restricting the comparison to the 66 tasks for which both No Memory and the final method produced a graded site gives means of 3.23 and 3.24, respectively.

\section{Why Text Memory Declines and Code Memory Holds}
\Cref{tab:prompt} records what entered the generator prompt, and \Cref{tab:codeerr} records code problems found by compiling each site with \texttt{@vue/compiler-sfc} 3.5.43. A lesson is classified as \emph{lacking a code construct} when it contains none of \texttt{@click}, \texttt{v-if}, \texttt{v-for}, \texttt{v-model}, \texttt{ref}, an \texttt{import}, or inline code. Such lessons, together with a ``General notes'' block, remain common in text memory. \section{Error Analysis}
Whole-site breaks fall from 26 tasks with No Memory to 17 with the final method, and to 8 with whole-file code memory. Missing Vue imports, however, remain as frequent as they are without memory: 4.6\% of components in both arms. Because the protocol does not allow repair, this remains a residual generator error.

The final method has 20 zero-score tasks, 11 of which are also zero under No Memory. Nine import an undeclared package: six import \texttt{vue-router}, while the others import chart, chess, or editor libraries. Three encounter a Vue compile error involving \texttt{v-model} on a file input or prop, three call a Vue function without importing it, and five render but fail every functional test. Only one returns the starter project. \texttt{vue-router} is imported without declaration in seven tasks, compared with three under whole-file code memory, even though the relevant fragment is injected in 88 tasks after activation. In manifest order, the fragment prevents this import less reliably than a complete file; under shuffled orders, complete files instead cause scaffold outputs (\Cref{sec:order-design}).


\section{Ablations: Checklist Only and Fixed Code Prefix}
\label{sec:ablation}
Two complementary ablations use the manifest order: a checklist-only control and a retrospective fixed-code control using the code entries learned by the final method:
\begin{itemize}
  \item \textbf{Checklist only:} the code-memory configuration with memory reads and writes disabled; each task sees only the requirement checklist. Checklist only $-$ No Memory estimates the effect of requirement decomposition.
  \item \textbf{Fixed code prefix:} checklist only, plus the code-pool entries that the final method had learned by the end of its manifest run (\Cref{sec:codepool}), injected from the first task with the same selection rule, still without memory. The code is not written by hand; it is the method's own learned content. Because it is taken from the end of a complete run, this control has access to experience that an online learner only gains later; it is a retrospective, oracle-style comparison rather than an online one. Fixed prefix $-$ checklist only estimates the effect of having this code in the prompt, and final method $-$ fixed prefix the effect of accumulating experience and selecting it per task.
\end{itemize}
If the fixed-code control performs similarly to the final method, the contribution is better described as automatically discovering effective prompt code from the agent's own failures and successes than as continual accumulation. The comparison does not isolate accumulation alone, because the two conditions also differ in textual lessons and memory maintenance.

\section{Robustness to Task Order}
\label{sec:order-design}
With memory, the order decides which experience is available; in the manifest order same-domain tasks are adjacent, so a gain could be a curriculum effect. We therefore compare two kinds of order, each run twice from an empty memory:
\begin{description}
  \item[Domains adjacent.] The order of the 20 domain blocks and the order of tasks within each block are shuffled, with seed 11 and seed 47. The manifest order, used for the main results, also belongs to this kind.
  \item[Domains mixed.] A uniformly random order of all 101 tasks (seed 29), and an interleaved order that takes one task from each domain in turn, so that consecutive tasks always come from different domains.
\end{description}
In these orders the two arms run as pairs on each task, alternating which runs first (ABBA). No Memory proved stable: generation is deterministic, and three runs scored 28.5, 27.9 and 28.6\% with 30, 29 and 29 zero-score tasks, so to save compute no further No Memory runs were made: it was stopped after 14 tasks of the interleaved order and after 90 tasks of seed 47. From then on only Long Memory runs, and these orders are compared with the existing No Memory scores per task.

\paragraph{Development and validation.} Seed 11 was used to develop the fragment fix (\Cref{sec:fix}) and is therefore development data for the final method. Its manifest, seed-29, seed-47 and interleaved runs started after it was frozen. All orders use the same 101 tasks, on which the method was developed, so this is a within-benchmark study with cross-order validation, not a held-out evaluation (\Cref{sec:threats}).

In both shuffled orders whole-file code memory leads by about 4.5 points, but neither interval excludes zero (\Cref{tab:order}); No Memory stays at 27.9--28.6\%, so the change is on the memory side. The whole-file design was itself developed on the manifest order: each step from text memory to whole-file code memory followed an inspection of failures in that run. Its 40.0\% there is therefore likely optimistic, a development-set effect rather than a property of the order, since it falls by about 7 points in both shuffled orders while No Memory does not move. The final method, frozen before all its runs except seed 11, varies less (33.7--35.4\% in the three complete orders). The random order matches the shuffled-blocks order, so the gain does not require adjacent same-domain tasks, although these runs do not measure how much adjacency contributes.

Both runs lose much of their gain to one failure (\Cref{fig:order-gap,fig:scaffold}): Long Memory returned the unmodified scaffold on 19 (seed 11) and 16 (seed 29) tasks, all after a complete \texttt{App.vue} from another site began to be injected; No Memory never did.

\paragraph{A positive case.} In the manifest order, task 000030 (13th) imported \texttt{vue-router}, which the template does not declare, and every test case failed. Static analysis recorded the undeclared import, and the code pool stored a page-switch fragment (a \texttt{ref}, navigation buttons and \texttt{v-if}, about 15 lines) taken from the 3rd task, a site that had scored 0.92 without a router. Its condition, a requirement with several pages to switch between, held for task 000059 (29th), a study-group site with four sections. \subsection{Fixing the Exposed Failure}
\label{sec:fix}
The fix was developed on seed 11 while all other experiments used the frozen whole-file design. It changes only the code pool. Every entry type now shows a fragment rather than a file: on the seven seed-11 tasks where the whole-file design had returned the scaffold, accuracy rose from 3.6\% to 45.2\%, and no scaffold occurred. An entry is replaced only when its new example covers strictly more of the needed functions, so that the example does not switch back and forth. Whole-site failures create an entry after one occurrence, since waiting for a second meant that rare problems were learned after they had already done their damage, and three slots are allowed instead of two. Compile-error entries apply to every Vue site. Total accuracy on seed 11 is not used to judge these changes: memory chains diverge from the first task, and two runs of the same design can differ by about five points. This is debugging evidence; the full-benchmark evidence for the final method is the set of runs started after it was frozen (\Cref{tab:order}).
