\section{Error Analysis}
Whole-site breaks fall from 26 tasks (No Memory) to 8 (v7), whereas pages with a missing Vue import are about as frequent as without memory (23 vs 22): the code pool prevents the error that blanks the whole site more reliably than the per-page one, which remains a basic error of the 7B generator. Counted per file, 27 of 592 generated Vue components in v7 (4.6\%) call a Vue function without importing it, against 27 of 586 (4.6\%) for No Memory. The omission occurs in \texttt{App.vue} and in child components alike, and is unrelated to whether a component uses \texttt{defineProps}/\texttt{defineEmits}; in the same file other imports are usually correct. The two arms show the same per-file rate, which is consistent with a slip rather than a misconception that an example could correct, though we have not shown this directly; a site with more components is more likely to contain one.

This slip was not reduced by a better example: a variant that showed both \texttt{ref} and \texttt{computed} removed it in one of four affected tasks. As the official protocol forbids repairing code after generation, we report it as a limitation of the generator. \section{Ablations: Checklist Only and Fixed Code Prefix}
\label{sec:ablation}
Two ablations separate the contributions of the components, both with the v7 configuration and the manifest order:
\begin{itemize}
  \item \textbf{Checklist only:} v7 with memory reads and writes disabled; each task sees only the requirement checklist. Checklist only $-$ No Memory estimates the effect of requirement decomposition.
  \item \textbf{Fixed code prefix:} checklist only, plus the code-pool entries that v9.1 had learned by the end of its manifest run (\Cref{sec:codepool}), injected from the first task with the same selection rule, still without memory. The code is not written by hand; it is the method's own learned content. Because it is taken from the end of a complete run, this control has access to experience that an online learner only gains later; it is a retrospective, oracle-style comparison rather than an online one. Fixed prefix $-$ checklist only estimates the effect of having this code in the prompt, and v9.1 $-$ fixed prefix the effect of accumulating experience and selecting it per task.
\end{itemize}
If the fixed prefix matches v7, the contribution of the method is better described as automatically discovering effective prompt code from the agent's own failures and successes than as continual accumulation.

\section{Generalisation to a Larger Generator}
\label{sec:stronger}
Does the memory framework also improve a larger generator from the same family? We repeat No Memory and the final version with WebGen-LM-32B, in the manifest order, keeping Bolt.diy, the memory pipeline and the evaluators unchanged. The 32B model is served in BF16, as in the original paper, where it reaches 38.2\% with Bolt.diy~\cite{lu2025webgenbench}; the two arms run concurrently on two lanes, so both experience the same infrastructure conditions. Deployment differs from the 7B runs: the 32B generator shares the second GPU with the memory model, which is restarted with a smaller memory share (0.42 of the GPU instead of 0.80, with the 32B model given 0.54); the evaluator and the 7B lanes stay on the first GPU. This comparison shows whether the full memory helps a stronger generator; it does not by itself show whether a larger model makes better use of text than of code, because the 32B runs have no text-memory arm. That question is left to future work.

\section{Robustness to Task Order}
\label{sec:order-design}
WebGen-Bench is a static benchmark: tasks are solved independently and its main results are single runs without error bars, which the authors attribute to computational cost~\cite{lu2025webgenbench}. With memory, however, the order of tasks determines which experience is available, so a single order is not sufficient evidence. In particular, in the manifest order tasks of the same domain are adjacent, so a later task can always draw on a just-solved, similar website; a gain could therefore reflect a curriculum effect rather than general learning.

We therefore compare two kinds of order, each run twice, every run starting from an empty memory:
\begin{description}
  \item[Domains adjacent.] The order of the 20 domain blocks and the order of tasks within each block are shuffled, with seed 11 and seed 47. The manifest order, used for the main results, also belongs to this kind.
  \item[Domains mixed.] A uniformly random order of all 101 tasks (seed 29), and an interleaved order that takes one task from each domain in turn, so that consecutive tasks always come from different domains.
\end{description}
In every order, Long Memory and No Memory are run as pairs on each task, alternating which arm runs first (ABBA), so that drift in infrastructure or evaluator load affects both arms equally. No Memory should not depend on order; its runs instead measure run-to-run noise (three completed, two running). The checklist-only ablation does not use memory and is run once. Results are task-level paired differences with bootstrap \glspl{ci}.

\paragraph{Development and validation.} Seed 11 was used to develop v8--v9.1 (\Cref{sec:fix}) and is therefore development data for the final version. The manifest, seed-29, seed-47 and interleaved runs of v9.1 started after v9.1 was frozen. All orders use the same 101 tasks, on which the earlier versions were developed, so this is a within-benchmark study with cross-order validation, not a held-out evaluation (\Cref{sec:threats}).

The first two shuffled orders give almost the same result (\Cref{tab:order}): Long Memory leads by about 4.5 points, with zero-score tasks reduced from 29 to 21, but neither confidence interval excludes zero, and the gain is far smaller than in the manifest order. No Memory is stable across its three runs (27.9--28.6\%), so the change is on the Long Memory side. Mixing domains does not remove the gain: the random order (seed 29) matches the shuffled-blocks order (seed 11), and from task 31 onwards Long Memory leads by 6.6 points in the random order (33.9\% vs 27.3\%). A curriculum effect from same-domain neighbours is therefore not the main source of the benefit.

Both runs lose much of their gain to the same failure (\Cref{fig:order-gap}). Long Memory returned the unmodified Vite scaffold on 19 tasks in seed 11 and 16 in seed 29, against none for No Memory in either order and two in the manifest order. Every scaffold occurred after the missing-package code memory, whose example was a complete \texttt{App.vue} of another site, began to be injected (task 36 in seed 11, task 19 in seed 29). This is the failure the v8 change targets (\Cref{sec:fix}).

Missing Vue imports remain (23 and 27 tasks with at least one affected component, against 17 and 19 for v7): once the generator writes real pages instead of the scaffold, it has more opportunities for this slip.

\subsection{Fixing the Exposed Failure}
\label{sec:fix}
The fix was developed on seed 11 while the frozen v7 was used for all other experiments. It addresses three properties of the code pool in turn.

\textit{Form of the example.} The scaffolds came from the one entry type that still showed a whole file. v8 therefore stores a fragment for every entry type. On the seven seed-11 tasks where v7 had returned the scaffold, accuracy rose from 3.6\% to 45.2\%, and no scaffold occurred in the 61 tasks of the partial run. Total accuracy on the other tasks is not informative here: their prompts already differed before the code pool, because memory chains diverge from the first task, and two runs of the same version can differ by about five points. Versions are therefore compared by mechanism counts.

\textit{Stability and coverage.} In v8 the missing-import example was rebuilt whenever the counts of missed functions changed, and it switched between two versions. v9 replaces an entry only when the new example covers strictly more of the needed functions. It also creates entries for whole-site failures after one occurrence, because waiting for a second occurrence meant that rare problems were learned after they had already occurred, and it allows three slots instead of two.

\textit{Applicability.} The compile-error entry of v9 carried an applicability condition that no requirement matched, so it was never injected. v9.1 applies compile-error entries to every Vue site and is the final version.

The evidence for these changes comes from small targeted checks and partial runs on seed 11; it is debugging evidence. The full-benchmark evidence for the final version is the set of runs started after it was frozen (\Cref{tab:order}).
