\chapter{Background and Related Work}
\label{chap:background}



\section{Website Generation Benchmarks}
\label{sec:bg-webgen}
A website consists of multiple files, build configuration, and interaction logic. A project may look complete while failing to start or rendering only a blank page. Recent benchmarks therefore execute generated projects and test them through their interfaces. Related benchmarks cover interaction with existing websites (Mind2Web and WebArena~\cite{deng2023mind2web,zhou2024webarena}), generation from screenshots (Design2Code~\cite{si2024design2code}), and repository repair (SWE-bench~\cite{jimenez2024swebench}).

WebGen-Bench~\cite{lu2025webgenbench} contains 101 website requirements across 20 application domains and 647 functional test cases. For each task, the generated project is installed and started, then a \gls{gui} agent based on WebVoyager~\cite{he2024webvoyager} executes the test cases and returns \emph{Pass}, \emph{Partial}, or \emph{Fail}. A separate \gls{vlm} assigns a landing-page appearance score from 1 to 5. The benchmark also introduces WebGen-LM, a set of generators fine-tuned from Qwen2.5-Coder~\cite{hui2024qwencoder} on agent trajectories. With the Bolt.diy scaffold, WebGen-LM-7B achieves 28.4\% accuracy and an appearance score of 2.5. Larger general models, including Qwen2.5-Coder-32B, score lower (9.5\%), leaving the 7B model sufficiently capable for improvements to be observable without being close to the benchmark ceiling.

WebGen-Bench evaluates a generator within an agent scaffold rather than in isolation. In the Bolt.diy scaffold used here, the model writes a project through a sequence of file actions. The scaffold applies those actions to a template project, installs dependencies, and starts a development server. The official protocol gives the generator one attempt: it does not run a build check or a repair loop, and a project that cannot start receives zero on all its functional test cases. Consequently, memory can affect only what the generator writes on its first attempt; it cannot repair an error after the benchmark has exposed it.

The benchmark reports single runs without error bars because repeated runs are costly~\cite{lu2025webgenbench}. It also defines no interaction between tasks. Once memory is introduced, task order becomes a treatment variable, which \Cref{sec:order-design} addresses explicitly.

\section{Memory for LLM Agents}
\label{sec:bg-memory}
An agent-memory system must decide what to store after a task, how to maintain that information, and how to retrieve it for a new task.

\paragraph{Text and code memory.} ExpeL~\cite{zhao2024expel} extracts natural-language insights from trajectories and maintains them through editing and voting. ReasoningBank~\cite{reasoningbank2025} distils strategies from successes and failures. Generative Agents~\cite{park2023generative} rank memories by recency, importance, and relevance. Reflexion~\cite{shinn2023reflexion} reuses self-reflections when retrying the same task. Voyager~\cite{wang2023voyager} and Agent Workflow Memory~\cite{wang2025awm} store skills or workflows. Metis~\cite{dai2026metis} promotes recurring plans to executable tools; with a GPT-4o executor these tools reach 53.3\% task completion, against 73.3\% for text memory. Synapse~\cite{zheng2024synapse}, Dynamic Cheatsheet~\cite{suzgun2026cheatsheet}, and ACE~\cite{ace2026} keep abstracted exemplars or an incrementally edited playbook. From this work, the present study adopts two maintenance principles: remove source-task details when possible, and version entries rather than overwriting them. Unlike Metis, the present method supplies code fragments to the generator as prompt content; it does not execute them as tools.

\paragraph{Transfer and cross-task reuse.} Memory Transfer Learning~\cite{kim2026mtl} reports that abstract insights transfer more effectively than concrete trajectories when strong models are used, while concrete trajectories can cause negative transfer. Neither that work nor Metis evaluates small models. Super Library Agent~\cite{sung2026superlibrary} generates WebGen-Bench applications sequentially with a shared component library. It focuses on maintainability, uses a strong backbone, evaluates 24 single-topic tasks, and reports no clear functional-accuracy improvement (76.04\% to 77.21\%). It neither stores lessons from failures nor varies task order.

\paragraph{Maintenance and task order.} Mem0~\cite{chhikara2025mem0} chooses whether a new memory should be added, update an existing entry, or be skipped. Memento~\cite{zhou2025memento} estimates case utility from outcomes, while MemGPT~\cite{packer2023memgpt} manages memory tiers. This study borrows write-time deduplication and a utility score. Evo-Memory~\cite{wei2025evomemory} and AgentCL~\cite{shu2026agentcl} show that the composition and ordering of a task stream can affect results. Accordingly, this dissertation compares orders with adjacent same-domain tasks and orders in which domains are mixed (\Cref{sec:order-design}).

\section{Small Models, Long Prompts and Instruction Following}
\label{sec:bg-small}
Adding information to a prompt has a cost. Models become less likely to satisfy all instructions as the number of instructions rises~\cite{harada2025curse,jaroslawicz2025ifscale}; information in the middle of a long context receives less attention than information near either end~\cite{liu2024lost}; irrelevant context can distract a model~\cite{shi2023distracted}; and longer inputs alone can reduce performance even when retrieval is accurate~\cite{du2025contextlength}. Models can be trained to prioritise instructions by source~\cite{wallace2024hierarchy}, which motivates keeping the user requirement above any memory content. Small models also benefit less consistently from long reasoning chains~\cite{li2025smallmodels}.

Although these findings largely come from reasoning and question-answering settings, they imply a practical risk for memory systems: a growing store adds text to every prompt and may obscure the requirement or supply advice that the generator cannot convert into code.

\section{Self-Correction and Debugging}
\label{sec:bg-selfcorr}
Reflection on failed attempts is related to Self-Refine~\cite{madaan2023selfrefine}, Self-Debug~\cite{chen2023selfdebug}, and Chain-of-Verification~\cite{dhuliawala2023cove}. Those methods repair the \emph{same} task using feedback. The formal comparison here does not allow that behaviour, because using hidden evaluation results to repair a benchmark task would leak the answer. Reflection is used only to write memory for \emph{later} tasks. The reflection model follows investigation steps adapted from systematic debugging~\cite{zeller2009whyprograms}.

\section{Research Gap}
\label{sec:gap}
\Cref{tab:related} compares the closest studies along the dimensions relevant to this dissertation. Three gaps follow. First, cross-task memory has almost exclusively been studied with large agents, leaving open whether a small generator benefits and what representation it can use. Second, the only cross-task WebGen-Bench study addresses maintainability with a strong backbone on single-topic suites and finds no clear functional-accuracy gain. Third, memory studies usually report a single task order even though the memory available for a task depends on earlier tasks.

This dissertation addresses these gaps by measuring memory effects on functional accuracy for a 7B generator while retaining the official single-attempt procedure within each task; by examining textual, checklist, and code-based memory across system versions, while recognising that these versions differ in more than representation; and by repeating comparisons under different task orders with task-paired confidence intervals.
