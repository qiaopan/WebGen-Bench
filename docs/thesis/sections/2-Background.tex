\chapter{Background and Related Work}
\label{chap:background}

This chapter covers website-generation benchmarks, memory for \gls{llm} agents, small models and added prompt text, and self-correction, and then states the research gap (\Cref{sec:gap}).

\section{Website Generation Benchmarks}
\label{sec:bg-webgen}
Code-generation benchmarks have moved from single functions towards whole applications. A website is a demanding target: it combines several files, a build configuration, a user interface and interaction logic, and a request in natural language usually lists several pages and features at once. Evaluating such output by reading the code is unreliable, because a project can look complete and still fail to start, or start and render a blank page. Recent benchmarks therefore start the generated project and test it through its interface. Related benchmarks test agents that operate existing websites, such as Mind2Web and WebArena~\cite{deng2023mind2web,zhou2024webarena}, generate a single page from a screenshot and compare it visually, as in Design2Code~\cite{si2024design2code}, or change a code repository and run its tests, as in SWE-bench~\cite{jimenez2024swebench}.

WebGen-Bench~\cite{lu2025webgenbench} contains 101 website requirements from 20 application domains, each paired with a set of functional test cases (647 in total). A generated project is installed and started, and a \gls{gui} agent based on WebVoyager~\cite{he2024webvoyager} executes each test case and returns \emph{Pass}, \emph{Partial} or \emph{Fail}. A separate \gls{vlm} grades the appearance of the landing page from 1 to 5. The authors also release WebGen-LM, generators fine-tuned from Qwen2.5-Coder~\cite{hui2024qwencoder} on agent trajectories; with the Bolt.diy scaffold, WebGen-LM-7B reaches 28.4\% accuracy and an appearance score of 2.5. Larger general models such as Qwen2.5-Coder-32B score lower (9.5\%), which makes the 7B model a good subject: it is neither at the floor nor at the ceiling of the benchmark.

WebGen-Bench evaluates generators inside agent scaffolds rather than as bare models. In the Bolt.diy scaffold used here, the model writes the project as a sequence of file actions in its reply, the scaffold applies them to a template project, installs dependencies and starts a development server. The official protocol gives the generator a single attempt: there is no build check and no repair loop, and a project that does not start receives zero for all of its test cases. This is important for our study, because it means memory cannot help by fixing errors after they happen; it can only change what the generator writes in the first place.

The benchmark reports single runs without error bars, citing computational cost, and defines no interaction between tasks~\cite{lu2025webgenbench}; with memory, task order becomes a treatment variable (\Cref{sec:order-design}).

\section{Memory for LLM Agents}
\label{sec:bg-memory}
An agent memory has three parts: what is written after a task (raw trajectories, insights, procedures or code), how it is maintained (added, merged, updated or forgotten), and how it is retrieved and presented to the model for a new task. Most work varies the first two and assumes the consuming model can use whatever is retrieved. The paragraphs below follow the same division and end with the question that matters most here: which form of memory transfers to a new task.

\paragraph{Experience and insight memory.} ExpeL~\cite{zhao2024expel} lets an agent collect trajectories, extract natural-language insights, and maintain them with add, edit, upvote and downvote operations. ReasoningBank~\cite{reasoningbank2025} distils reusable reasoning strategies from both successful and failed trajectories. Generative Agents~\cite{park2023generative} rank memories by recency, importance and relevance. Reflexion~\cite{shinn2023reflexion} stores verbal self-reflections after a failed attempt, but reuses them on retries of the same task rather than on new tasks.

\paragraph{Skill and code memory.} Voyager~\cite{wang2023voyager} stores executable skills as code and retrieves them by description; Agent Workflow Memory~\cite{wang2025awm} stores reusable workflows. Metis~\cite{dai2026metis} promotes recurring plans to validated tools that the agent executes; with a GPT-4o executor and memory built only from earlier tasks, its code memory reaches 53.3\% task completion against 73.3\% for text memory, brittle under task variation. Our fragments are different: they are placed in the prompt to be imitated, not executed.

\paragraph{Exemplars and evolving context.} Synapse~\cite{zheng2024synapse} abstracts earlier trajectories before using them as exemplars, Dynamic Cheatsheet~\cite{suzgun2026cheatsheet} keeps strategies and code snippets updated at inference time, and ACE~\cite{ace2026} edits a context playbook incrementally to avoid losing detail. Two lessons shaped our design: examples should be stripped of details from their source task, and entries should be versioned rather than rewritten.

\paragraph{Which form of memory transfers.} Memory Transfer Learning~\cite{kim2026mtl} finds, with strong models, that abstract insights transfer best across domains and concrete trajectories can transfer negatively. Neither it nor Metis tests small models; our results suggest that the preferred form depends on the model that must use the memory.

\paragraph{Cross-task reuse on WebGen-Bench.} Super Library Agent~\cite{sung2026superlibrary} also builds WebGen-Bench applications in sequence, sharing a library of components. It targets maintainability: on 24 single-topic tasks with a strong backbone, accuracy changes insignificantly (76.04\% to 77.21\%) while code size falls. It stores no lessons from failures and does not vary task order; we study correctness with a small generator on all 101 tasks, with order as a variable.

\paragraph{Memory maintenance.} Mem0~\cite{chhikara2025mem0} decides at write time whether a new memory should be added, should update an old one, or is redundant. Memento~\cite{zhou2025memento} learns the utility of stored cases from their outcomes. MemGPT~\cite{packer2023memgpt} manages several tiers of memory for long interactions. Our hygiene component borrows these ideas: deduplication at storage time and a utility score for each memory.

\paragraph{Task order in continual agent evaluation.} Benchmarks for agents that learn across tasks report that the order and composition of the task stream affect results. Evo-Memory~\cite{wei2025evomemory} finds that baselines vary substantially between easy-to-hard and hard-to-easy sequences, and AgentCL~\cite{shu2026agentcl} shows that memory methods can only be distinguished on streams that expose opportunities for reuse. We therefore compare orders in which tasks of the same domain are adjacent with orders in which they are mixed (\Cref{sec:order-design}).

\section{Small Models, Long Prompts and Instruction Following}
\label{sec:bg-small}
Several results suggest that adding text to a prompt is not free. Models become less likely to satisfy all instructions as their number grows~\cite{harada2025curse,jaroslawicz2025ifscale}; information in the middle of a long context is used less than at its start or end~\cite{liu2024lost}; irrelevant context distracts models~\cite{shi2023distracted}; and longer inputs alone can reduce performance even with perfect retrieval~\cite{du2025contextlength}. Models can be trained to prioritise instructions by source~\cite{wallace2024hierarchy}, which motivates keeping the user requirement explicitly above any memory content. Small models also struggle to benefit from long reasoning chains~\cite{li2025smallmodels}, which is consistent with our negative result for a short planning step (\Cref{sec:history}).

These findings were obtained mostly on reasoning and question-answering tasks, but they point to a specific risk for memory. A memory that grows with experience adds more and more text to every prompt. For a large model this may be harmless; for a small one it may bury the user's requirement, introduce instructions that conflict with it, or present advice the model cannot turn into code. Whether a small generator can use memory at all, and in which form, therefore cannot be assumed from results obtained with large models.

\section{Self-Correction and Debugging}
\label{sec:bg-selfcorr}
Reflection on failed attempts is related to self-correction methods such as Self-Refine~\cite{madaan2023selfrefine}, Self-Debug~\cite{chen2023selfdebug} and Chain-of-Verification~\cite{dhuliawala2023cove}. These methods repair the \emph{same} task with feedback. We do not allow this in the formal comparison, because repairing a benchmark task using its hidden evaluation results would leak the answer. Reflection is used only to write memory for \emph{later} tasks. The investigation steps we ask the reflection model to follow are modelled on systematic debugging~\cite{zeller2009whyprograms}.

\section{Research Gap}
\label{sec:gap}
\Cref{tab:related} compares the closest studies along the dimensions that matter for this dissertation. Three gaps follow from it. First, cross-task memory has been studied almost only with large agents; whether a small generator benefits, and from which form of memory, remains underexplored. Second, on WebGen-Bench the only cross-task study targets maintainability with a strong backbone on single-topic suites, and reports no clear improvement in functional accuracy. Third, memory results are usually reported for a single task order, although the memory available to a task depends on the tasks before it. This dissertation addresses all three: it measures the effect of memory on functional accuracy for a 7B generator, retaining the official single-attempt procedure within each task and adding memory only between tasks; examines how textual, checklist and code-based memory behave across successive system versions (which differ in more than representation); and repeats the comparison under different task orders with task-paired confidence intervals.
