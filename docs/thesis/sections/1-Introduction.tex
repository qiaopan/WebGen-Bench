\section{Background}
\subsection{Website Generation with Language Models}
\Gls{llm} agents can translate a natural-language requirement into a runnable website~\cite{lu2025webgenbench}. WebGen-Bench evaluates this capability end to end. It starts the generated project and uses a \gls{vlm} tester to check requested features through the interface~\cite{lu2025webgenbench,he2024webvoyager}. A website that appears plausible but does not support the required interactions therefore does not pass.

The strongest benchmark results use large proprietary models. Smaller open models are attractive for a different set of reasons: they can run locally, cost less to operate, and do not require task data to be sent to a third party. WebGen-LM-7B, the 7-billion-parameter generator released with WebGen-Bench, was fine-tuned for this setting but reaches 28.4\% accuracy under the official protocol~\cite{lu2025webgenbench}. Improving such a model without retraining is therefore a practical problem as well as a research question.

\subsection{Every Task Is Solved in Isolation}
WebGen-Bench, like most code-generation benchmarks, treats each task independently. The agent begins every task with the same weights and an empty context. If it produces a blank page because it imports a package that is not installed, the same failure can recur on the next task. In our baseline reproduction (\Cref{sec:nm-failures}), almost one third of the 101 tasks received zero. Many shared a small number of causes: an undeclared dependency, a missing import, or a template that did not compile.

A developer would normally avoid a build error after encountering it once. This study asks whether an agent can retain and use that kind of experience across tasks.

\subsection{Long-Term Memory for Agents}
Agent-memory systems aim to support this form of reuse. After a task, an agent may reflect on what occurred, store a lesson or procedure, and retrieve it when a related task appears later~\cite{zhao2024expel,wang2023voyager,reasoningbank2025,wang2025awm,dai2026metis}. Most such systems use large models and store memory as natural-language insight. Small models are a harder case. They follow multi-instruction prompts less reliably~\cite{harada2025curse,jaroslawicz2025ifscale,li2025smallmodels}, are distracted by irrelevant context~\cite{shi2023distracted}, and lose accuracy as prompts grow~\cite{du2025contextlength,liu2024lost}. Every stored lesson lengthens the prompt, so a memory that helps a large model can bury the requirement for a 7B generator or give it advice it cannot turn into code. Which \emph{form} of memory such a generator can use remains open.

\section{Problem Statement}
This dissertation examines whether a system built around a small website generator can improve through experience without changing the generator's weights. Here, \emph{long-term memory} means information written after one task, retained across subsequent tasks, retrieved under an explicit condition, and added to later prompts. \emph{Learning} therefore refers to an outcome-dependent change in the system's later behaviour that is carried by external memory. The generator parameters remain fixed, while a separate, larger memory model maintains the memory (\Cref{chap:setup}).

The study uses WebGen-Bench with WebGen-LM-7B. The generator, Bolt.diy scaffold, and official evaluation protocol are held constant. The treatment changes only the generator prompt through an external memory pipeline, which also adds computation (\Cref{chap:discussion}). Memory is derived solely from earlier tasks completed by the agent and their evaluation outcomes. The hidden evaluation for the current task is never used, preserving a fair comparison with the no-memory baseline.

This setting makes cross-task memory difficult to assess for two reasons. First, tasks arrive sequentially, so the memory available for a task depends on the tasks that precede it; results may therefore vary with task order. Second, the official protocol permits only one attempt per task. The memory must help the model avoid an error before it occurs rather than repair it afterwards.

\section{Research Questions}
\begin{questions}[itemindent=1.5em]
    \item Can cross-task long-term memory, built only from an agent's earlier tasks, improve the functional accuracy of a small website generator under the official WebGen-Bench protocol? \label{rq1}
    \item Which form of memory can a small generator use effectively: textual lessons, structured requirement checklists, or code examples? \label{rq2}
    \item How does any benefit change as experience accumulates, and how sensitive is it to the order in which tasks are presented? \label{rq3}
\end{questions}

\ref{rq3} separates learning from experience from a fixed prompt change that would help equally at every point in a run. The fixed-prefix ablation (\Cref{sec:ablation}) is designed to test this distinction.

\section{Scope}
The study is intentionally narrow so that the comparisons remain interpretable.
\begin{itemize}
    \item \textbf{One benchmark, generator, and scaffold.} All experiments use the 101 WebGen-Bench tasks, WebGen-LM-7B, and Bolt.diy. Larger generators and alternative agent scaffolds, such as OpenHands and Aider, are outside the study because changing the agent would also change how memory reaches the model.
    \item \textbf{Official protocol without repair.} Each website is generated once and evaluated as produced, following the original benchmark. Build checks and repair loops are excluded because they would make the comparison with the published baseline less direct.
    \item \textbf{No retraining.} Memory changes the prompt only. Fine-tuning the generator on stored experience is beyond the scope of this work.
    \item \textbf{Self-hosted models only.} Generation, evaluation, and memory processing run on a university GPU cluster; no commercial API is used.
\end{itemize}

\section{Contributions}
\begin{enumerate}
    \item A fully self-hosted reproduction of the WebGen-Bench no-memory baseline for WebGen-LM-7B (28.5\% versus the reported 28.4\%), together with a failure analysis showing that many zero scores arise from blank pages caused by basic code errors (\Cref{chap:setup,sec:nm-failures}).
    \item A long-term memory pipeline for website generation consisting of a requirement checklist, a code pool containing fragments copied verbatim from the chain's own compiled websites, and memory-hygiene rules. Each component was introduced in response to an observed failure in an earlier version (\Cref{chap:method}).
    \item Evidence that, in these runs, short code fragments reduced targeted failures for this small generator where textual lessons did not, together with an ablation that separates the checklist from stored cross-task content (\Cref{chap:results}).
    \item A task-order study using alternating paired runs. It shows that a memory entry can become harmful under a different ordering and that replacing whole-file examples with fragments removes that specific failure mode (\Cref{sec:order-design,sec:fix}).
\end{enumerate}
