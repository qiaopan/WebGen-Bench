\chapter{Discussion}
\label{chap:discussion}

\section{Form Matters More Than Amount}
The central observation of this work is that a small generator uses memory very selectively. Textual lessons, even correct and relevant ones, were rarely followed, and generic ones accumulated and displaced useful content. Short verified code fragments were followed. This agrees with Metis's finding that code memory complements text memory~\cite{dai2026metis}, and adds that for a 7B generator the format of the memory can decide whether it helps at all. The form of the code also matters: a fragment that looked like a complete file was copied as a finished answer, producing an untouched scaffold.

This contrasts with strong models, for which text memory transfers more reliably than code~\cite{dai2026metis,kim2026mtl}. The mechanisms differ (Metis executes its code; we show code to the generator), but together the results suggest that the best form of memory depends on the capability of the model that consumes it.

A second observation is that part of the gain is not ``smarter'' code but protection against collapse. In the earliest phase, short prompts made the model return the default scaffold in five of eight tasks, while longer, specific prompts did not. Both effects are real benefits of memory, but they should be described separately.

\section{Limitations and Threats to Validity}
\label{sec:threats}
\begin{itemize}
  \item \textbf{Single runs.} WebGen-Bench itself reports single runs without error bars. We go further by repeating No Memory five times to measure run-to-run noise and by repeating Long Memory under four additional orders with paired comparisons, but within each order Long Memory is still a single run, so per-task conclusions remain weak.
  \item \textbf{One generator and one scaffold.} All results are for WebGen-LM-7B with Bolt.diy and a Vue template. Larger generators may follow text well and benefit less from code fragments.
  \item \textbf{Residual generator errors.} About 4.6\% of generated components omit a Vue import with or without memory; examples did not reduce this random slip, and the protocol forbids repairing it after generation.
  \item \textbf{Code pool as a learned prefix.} Because its triggers are general, the code pool behaves partly like a fixed prompt prefix; the fixed-prefix ablation (\Cref{sec:ablation}) measures how much of the gain this explains.
  \item \textbf{Rare problems are learned late.} A code memory needs a problem to recur before it exists, so learning pays off mainly for frequent problems. In v7 the \texttt{vue-router} and \texttt{v-model} problems each occurred in only two seed-11 tasks, and with two slots the \texttt{v-model} memory was never injected although later tasks failed with that error. v9.1 creates memories for whole-site failures after one occurrence and allows three slots, but a problem seen once can still cost one task, and with other generators more problem types would compete for the slots.
  \item \textbf{Appearance grader.} We grade appearance with Qwen2.5-VL-32B instead of GPT-4o, so appearance scores are compared only between our arms. On tasks where both arms produce a working site, appearance is unchanged (3.25 vs 3.22), so our gains are functional only.
  \item \textbf{Iterative development on the same benchmark.} This is the most serious threat. Every version was designed after looking at failures on the same 101 tasks on which it is evaluated, so the design is in effect tuned on the test set. Four facts limit, but do not remove, the risk. Reflection rules teach a method of investigation and never a task-specific answer; memory content is learned from earlier tasks only and every run starts empty; the split into the first 30 and the last 71 tasks was fixed before v7 was run; and the final version was confirmed on two shuffled orders that it had not been developed on. A clean estimate would freeze the method on a development subset and report it once on held-out tasks; we leave this to future work (\Cref{chap:conclusion}).
  \item \textbf{Evaluator noise.} \gls{gui} testers can exhaust their interaction budget or misjudge pages~\cite{zheng2023judge}. We keep raw evaluator transcripts and distinguish interaction-budget exhaustion from logic failures. \todo{After a manual check of 20 sampled test cases (stratified by Yes/Partial/No and by arm), report the agreement between the tester and a human reader here.}
  \item \textbf{Memory model stronger than generator.} The 72B memory model is larger than the 7B generator, so part of the gain could be the larger model solving the task for the small one. Three observations argue against this reading. The checklist only restates the requirement, and on its own it gives no significant gain (\Cref{tab:ablation}). Every code fragment is copied verbatim from a website that the 7B generator itself built earlier, and code checks reject lines that are not in that file. And the memory model never sees the current task's evaluation. The results therefore show what a small generator gains when a stronger model organises its own past experience, not self-improvement in isolation. \todo{After the fixed-prefix run, state how much of the gain remains without learning.}
\end{itemize}

\section{Ethical Considerations and Impact}
\paragraph{Data and privacy.} The benchmark requirements are synthetic and contain no personal data. All models run on university hardware; no task data were sent to external services.
\paragraph{Environmental cost.} Each full run of 101 tasks takes about a day on two H200 GPUs, and the study required many runs. We reduced cost by testing changes on three to five tasks, by checking generated code statically before evaluating, and by avoiding repeated validations.
\paragraph{Self-improving code agents.} A memory that turns observed outcomes into future behaviour can also entrench mistakes or unsafe patterns. Our design keeps full provenance of every memory, requires code examples to compile, and never edits the source record, so that any injected content can be traced back to the task that produced it. Deployed systems would additionally need review of stored code for security.
\paragraph{Economy and society.} Tools that let small, locally hosted models build working websites lower the cost of software creation and keep data on local infrastructure, which may benefit small organisations. They may also reduce demand for routine front-end work. Generated websites still require human review for correctness and accessibility.
\paragraph{Use of AI tools.} \todo{Confirm course policy with the supervisor.} AI assistants were used for programming, organising experiment logs and editing English. The research questions, experimental design, analysis and conclusions are the author's own, and every number in this dissertation was computed from the archived runs.
\paragraph{Research integrity.} We report negative results (short \gls{cot}, the scaffold regression in v6, v4's decline) and invalidated our own earlier results when a delivery bug was found.

\section{Project Management}
The project was organised in versions. The cluster ran one frozen version at a time; new ideas were tested locally on small samples and with static code checks, and a version was replaced only when the new one was shown to be better. Decisions and their evidence were recorded continuously in a decision log, which made it possible to reconstruct why each component exists.
