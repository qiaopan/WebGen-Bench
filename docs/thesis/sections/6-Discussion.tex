\chapter{Discussion}
\label{chap:discussion}

\section{The Role of Memory Representation}
Across the diagnostic and the full runs, this small generator responded more reliably to short code fragments than to accumulated textual lessons. Because the text and code designs differ in more than representation, this is a cross-version observation, not a controlled comparison. This agrees with Metis's finding that code memory complements text memory~\cite{dai2026metis}, and adds that for a 7B generator the format of the memory can decide whether it helps at all. The form of the code matters in both directions: a complete file was copied as a finished answer, while a fragment prevented undeclared imports less reliably.

This contrasts with strong models, for which text memory transfers more reliably than code~\cite{dai2026metis,kim2026mtl}. The mechanisms differ (Metis executes its code; we show code to the generator), but together the results suggest that the best form of memory depends on the capability of the model that consumes it.

A second observation is that part of the gain is not ``smarter'' code but protection against collapse. In the earliest phase, short prompts made the model return the default scaffold in five of eight tasks, while longer, specific prompts did not. Both effects are real benefits of memory, but they should be described separately.

\section{What Is Learned and at What Cost}
The generator does not change; what changes is which code is shown to it, and when. This is closer to building a small set of preventive code examples than to acquiring programming ability, and it is a property of the whole system, including a memory model larger than the generator. Within 101 tasks the memory stays small; behaviour over thousands of tasks, with more problem types competing for three slots, is not tested.

The system is also not cheap: a Long Memory task takes about 12 minutes against about 6 for No Memory, mostly for checklist construction, applicability judgements and reflection by the 72B model. If the fixed-prefix ablation recovers most of the gain, a deployed system could use the learned fragments without the 72B model, at the cost of online adaptation.

\section{Limitations and Threats to Validity}
\label{sec:threats}
\begin{itemize}
  \item \textbf{Single runs.} WebGen-Bench itself reports single runs without error bars. We repeat No Memory under several orders to measure run-to-run noise (three runs completed, two running) and repeat Long Memory under additional orders with paired comparisons, but within each order Long Memory is still a single run. Two runs of the same Long Memory version can differ by about five points, more than No Memory varies, so the task-level intervals understate the full uncertainty. Orders share the same 101 tasks, so they are not independent samples. \todo{Status: a second manifest run of the final method is queued (about 10-19); report the difference between the two runs.}
  \item \textbf{Gain beyond the checklist and the trade-off between forms.} For the final method, the paired gain over checklist only is $+3.7$ ($[-1.8, 9.1]$), so a benefit beyond requirement decomposition is not established; whole-file examples prevented undeclared imports more reliably in the original order, so neither form is better everywhere.
  \item \textbf{One generator and one scaffold.} All results are for WebGen-LM-7B with Bolt.diy and a Vue template. Larger generators may follow text well and benefit less from code.
  \item \textbf{Code pool as a learned prefix.} Because its triggers are general, the code pool behaves partly like a fixed prompt prefix; the fixed-prefix ablation (\Cref{sec:ablation}) measures how much of the gain this explains.
  \item \textbf{Rare problems are learned late.} A safeguard exists only after a problem has occurred, so memory helps frequent problems more than rare ones, and with three slots several problem types can compete for space (\Cref{sec:fix}).
  \item \textbf{Evaluators.} Appearance is graded by Qwen2.5-VL-32B instead of GPT-4o, so it is compared only between our arms. \gls{gui} testers can exhaust their interaction budget or misjudge pages~\cite{zheng2023judge}; we keep raw transcripts, but judgements were not checked against a human reader.
  \item \textbf{Iterative development on the same benchmark.} This is the most serious threat. Every version was designed after looking at failures on the same 101 tasks on which it is evaluated. Empty starting memories and freezing the final version before all runs except seed 11 limit the risk without removing it; held-out evaluation is future work.
  \item \textbf{Memory model stronger than generator.} The 72B memory model is larger than the 7B generator, so part of the gain could be the larger model solving the task for the small one. Against this, the checklist only restates the requirement, every fragment is copied verbatim from a site the 7B generator built earlier, and the memory model never sees the current task's evaluation. The results show what a small generator gains when a stronger model organises its own past experience, not self-improvement in isolation. \todo{Status: fixed-prefix run queued after seed 47. \section{Ethical Considerations and Impact}
\paragraph{Data and privacy.} The benchmark requirements are synthetic and contain no personal data. All models run on university hardware; no task data were sent to external services.
\paragraph{Environmental cost.} A full run takes about a day on two H200 GPUs (\Cref{sec:design}); we limited runs by testing changes on three to five tasks and checking code statically before evaluation.
\paragraph{Self-improving agents and society.} A memory that turns outcomes into behaviour can entrench mistakes; our design keeps provenance of every memory so injected content can be traced, but deployed systems would need security review of stored code. Small local models that build websites lower costs for small organisations but may reduce routine front-end work, and their output still needs human review.
\paragraph{Use of AI tools.} Claude and ChatGPT were used to assist with programming the experimental pipeline and analysis scripts, organising experiment logs, and giving suggestions in critical reviews of drafts; Gemini and Microsoft Copilot were also used for review comments. All text was written by the author, who decided which suggestions to adopt. Research decisions and the verification of all results are the author's responsibility; every number was computed by the scripts in the public repository and checked by the author. \todo{Author: this statement holds only after the final text has been rewritten in your own words; check it against what was actually done before submission.}

\paragraph{Research integrity.} We report negative results (text memory's decline, the scaffold failure of whole-file examples) and invalidated our own earlier results when a delivery bug was found.

\section{Project Management}
The project was organised in versions. The cluster ran one frozen version at a time; new ideas were tested locally on small samples and with static code checks, and a version was replaced only when the new one was shown to be better. Decisions and their evidence were recorded continuously in a decision log, which made it possible to reconstruct why each component exists.
